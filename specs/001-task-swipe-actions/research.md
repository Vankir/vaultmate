# Phase 0 Research: Task List Swipe Actions

All items from the spec had reasonable defaults or were resolved during `/speckit-specify`
clarification; no `[NEEDS CLARIFICATION]` markers remain in `spec.md`. This phase records the
technical decisions needed to move from spec to design.

## Decision: Use Flutter's built-in `Dismissible`, not a third-party swipe package

**Decision**: Implement all four swipe behaviors with Flutter's built-in `Dismissible` widget.

**Rationale**: The spec describes direct swipe-to-commit actions ("swipe left means X happens"),
not a reveal-a-button-then-tap interaction. `Dismissible` matches that exactly: it exposes
`direction: DismissDirection.horizontal`, separate `background` / `secondaryBackground` widgets
per swipe direction, an `onDismissed` callback, and a `confirmDismiss` async callback — the last
of which is the natural hook for the delete confirmation prompt on Inbox (return `false` to cancel
and have the row snap back). It ships with the Flutter SDK already in `pubspec.yaml`, so it
requires no new dependency, directly satisfying Constitution Principle V (justify new
dependencies).

**Alternatives considered**:
- `flutter_slidable`: richer action-panel UI (multiple revealed buttons), but that's a different
  interaction model than what was requested, and it would be a new dependency with no
  corresponding requirement in the spec.
- Custom `GestureDetector` + `AnimatedContainer`: full control, but reimplements what
  `Dismissible` already provides (drag tracking, thresholds, snap-back, direction-aware
  callbacks) for no benefit here.

## Decision: Confirmation prompt reuses the existing `AlertDialog`/`showDialog` pattern

**Decision**: The Inbox swipe-right delete confirmation is a standard `AlertDialog` shown via
`showDialog`, matching the pattern already used elsewhere in `lib/src/screens/inbox_tasks/`.

**Rationale**: `inbox_tasks.dart` and `main_messages.dart` already use `showDialog`/`AlertDialog`
for other prompts in this screen. Reusing the same widget keeps a single confirmation-dialog style
in the app (Constitution Principle V — no new pattern for something already solved) and lets
`confirmDismiss` simply `await` the dialog's result.

**Alternatives considered**: A `SnackBar` with an "undo" action instead of a blocking
confirmation. Rejected because the spec explicitly requires confirmation *before* deletion
("confirmation to delete is requested and after confirmation task should be deleted"), not
delete-then-offer-undo.

## Decision: New `TaskManager` methods follow the existing `scheduleForToday`/`removeFromToday` shape

**Decision**: Add `Future scheduleForTomorrow(Task task)` and `Future deleteTask(Task task)` to
`TaskManager`, structured like the existing pair:

```dart
Future scheduleForTomorrow(Task task) async {
  task.scheduled = DateTime.now().add(const Duration(days: 1));
  if (task.taskSource != null) {
    await saveTask(task);
  }
}
```

`deleteTask` removes the task from its source file and persists the remaining tasks for that file
(see `data-model.md` for exact save-path handling), then relies on the existing
`saveTasks(...) → notifyListeners()` call already present in `TaskManager`, which is what the
current Plus/Minus buttons depend on for both in-app list refresh and home-screen widget sync — no
new sync mechanism is required.

**Rationale**: Every other task-mutation action in this codebase (`changeTaskStatus`,
`scheduleForToday`, `removeFromToday`) goes through `saveTask`/`saveTasks`, which already
re-parses the affected file and calls `notifyListeners()`. Following the same shape means the new
actions automatically inherit correct list refresh and widget-sync behavior, and keeps
`InboxTasksCubit` a thin pass-through, consistent with Constitution Principle V.

**Alternatives considered**: A generic `updateTask(Task, {DateTime? scheduled, bool delete})`
method. Rejected as unnecessary indirection for two clear, independently named actions — matches
the existing one-method-per-action style already in this class.

## Decision: Delete removes only the current occurrence; recurrence rule is untouched

**Decision**: `deleteTask` never inspects or modifies `task.recurrenceRule`. It only removes the
one task line being deleted.

**Rationale**: Confirmed with the user during `/speckit-specify` clarification (spec.md, Edge
Cases / FR-010). The next occurrence of a recurring task is only generated by
`_manageRecurrentTask` when an occurrence is marked done (see `task_manager.dart`), never on
delete — so deleting a recurring task's current occurrence is expected to end the series, and no
extra logic is needed to "clean up" the recurrence rule separately.

## Decision: Swipe wraps every call site of `_createTaskCard`, not just the main list

**Decision**: The `Dismissible` wrapper is added inside `_createTaskCard` in `inbox_tasks.dart`
(the single method that builds every `TaskCard` instance in this screen), rather than only at the
main `ListView.builder` call site.

**Rationale**: `_createTaskCard` is reused for the main list, calendar-view results, and
file/search results — all within the same Today/Inbox screen and sharing the same `today` context.
Wrapping there keeps swipe behavior consistent everywhere a task row appears in this screen,
instead of only in one of several list-rendering paths.

**Alternatives considered**: Wrapping only the primary `ListView.builder` (line ~417). Rejected —
would leave calendar/search results in the same screen without the swipe affordance while their
Plus/Minus buttons (via the same `_createTaskCard`) are being removed, producing an inconsistent,
now-button-less row with no replacement gesture.
